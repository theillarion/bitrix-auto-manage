## Часть 1. Вебхук Bitrix24

### Что такое входящий вебхук

Входящий вебхук — постоянный адрес REST API вида:

```
https://<адрес-портала>/rest/<USER_ID>/<КОД>/
```

Любой запрос к этому адресу выполняется **от имени сотрудника, создавшего
вебхук** (владельца). Отдельный OAuth-токен не нужен. Проект использует методы
`profile` и `crm.item.*` (чтение и создание карточек смарт-процессов CRM),
поэтому вебхуку достаточно области прав **«CRM»**.

Владелец вебхука — это сотрудник, на которого создаются удалёнка, рабочий день
и записи учета времени. Вести нескольких сотрудников одним вебхуком нельзя:
создавайте вебхук из аккаунта того, за кого ведётся учёт.

### Создание по шагам

1. Войдите на портал под аккаунтом сотрудника, за которого ведётся учёт
   (обычно свой собственный).
2. На главной странице в левом меню нажмите **«Показать все»**.
3. В группе **«Приложения»** выберите пункт **«Разработчикам»**.
4. На странице «Разработчикам» выберите плитку **«Другое»**
   («Создайте входящий вебхук, исходящий вебхук или локальное приложение»).
5. Выберите **«Входящий вебхук»** («Создайте входящий вебхук, для работы
   с данными вашего Битрикс24 через API»).
6. Откроется форма, в которой портал сразу генерирует URL в поле
   «Вебхук для вызова rest api» вида
   `https://портал/rest/12345/a1b2c3d4…/`. Задайте название вебхука
   (карандаш рядом с заголовком), например `bitrix-auto-manage`.
7. Внизу формы в секции **«Настройка прав»** нажмите «+ выбрать» и отметьте
   область **«CRM»**. Этого достаточно: методы `profile` и `method.get`
   входят в базовый доступ. Если `check` пожалуется на чтение профиля —
   дополнительно отметьте «Пользователи».
8. Нажмите **«Сохранить»**. Скопируйте URL из поля «Вебхук для вызова
   rest api» целиком, **вместе со слэшем на конце** — он входит в формат.
9. Впишите URL в `.env` (файл создаётся копированием из `.env.example`):

   ```dotenv
   BITRIX_WEBHOOK_URL=https://портал/rest/12345/a1b2c3d4e5f67890/
   BITRIX_TIMEZONE=Europe/Moscow
   ```

Из чего состоит URL:

| Часть | Значение |
|---|---|
| `https://портал` | адрес вашего портала (`имя.bitrix24.ru` или собственный домен) |
| `/rest/` | корень REST API |
| `12345` | USER_ID — владелец вебхука, номер сотрудника |
| `a1b2c3d4e5f67890` | секретный код вебхука (около 20 символов) |
| `/` на конце | обязательный завершающий слэш |

### Проверка

В проекте две консольные утилиты: `bitrix-auto` — CLI этого пакета (он же
точка входа контейнера) и `bitrix-time` — CLI соседнего SDK. Если вы
работаете через Docker, команды `bitrix-auto` даются через
`docker compose run` — это создаст одноразовый контейнер с теми же `.env`
и `config/`:

```bash
docker compose run --rm bitrix-auto check
```

Команда проверяет без единой записи: соединение и владельца вебхука
(`profile`), схему смарт-процессов портала (поля рабочих дней, удалёнки и
учета времени) и доступность метода `crm.item.add`. Успех — JSON-отчёт со
`schema_ok: true`. Дополнительно можно прочитать уже существующий день:

```bash
docker compose run --rm bitrix-auto show --date 2026-10-20
```

При локальном запуске без Docker те же команды выполняются утилитой
`bitrix-auto` из активированного venv (см. README): `bitrix-auto check`,
`bitrix-auto show --date 2026-10-20`.

### Безопасность и срок действия

- **URL вебхука — это секрет.** Любой, кто его знает, может действовать от
  имени владельца в пределах выданных прав (включая создание карточек CRM).
  Не вставляйте URL в YAML-расписания, коммиты, чаты и скриншоты — портал
  не зря показывает на форме красное предупреждение. Файл `.env` исключён
  из Git — храните URL только там.
- Если URL всё же попал куда-то лишний раз, нажмите **«Перегенерировать»**
  в карточке вебхука: портал выдаст новый секретный код, а старый URL
  сразу перестанет работать. После этого обновите `.env`.
- Вебхук не истекает сам по себе, но администратор портала может отключить
  или удалить его. Если автоматика вдруг стала получать ошибки доступа —
  проверьте, что вебхук активен и область «CRM» отмечена в «Настройке прав».
- Права самого владельца тоже должны включать доступ к используемым
  смарт-процессам (карточки договоров 1048/1052, шаблоны 1298): вебхук не
  может больше, чем его владелец.

### Частые ошибки вебхука

| Симптом | Причина и решение |
|---|---|
| `ACCESS_DENIED` от `crm.item.add` | В правах вебхука не отмечена область «CRM», либо у владельца нет прав на запись в смарт-процесс. |
| `The webhook belongs to a different user` | Вебхук выдан не на того сотрудника, чей USER_ID в URL, либо URL скопирован частично. Пересоздайте и скопируйте целиком. |
| `Invalid webhook URL` / ошибка формата | URL без `https://`, без завершающего слэша или с лишними символами. |
| `SchemaError` при `check` | Портал другой конфигурации (нет ожидаемых смарт-процессов и полей). Схема проверена на конкретном портале; см. README SDK, раздел «Поведение портала». |

## Часть 2. Файл расписания

### Где живёт и как загружается

Расписание — один или несколько YAML-файлов в каталоге `config/`:

- каталог читается при каждом запуске; файлы `*.yaml` и `*.yml` применяются
  **по алфавиту**;
- файлы с `.example.` в имени игнорируются — это шаблоны, а не настройки;
- скалярные значения и секция `schedule` из позднего файла перезаписывают
  ранние, а списки `tasks` объединяются;
- если в каталоге нет ни одного подходящего файла, запуск завершится ошибкой
  `No settings YAML files found in config`.

Минимальный вариант — один файл `config/schedule.yaml`, созданный командой:

```bash
cp config/schedule.example.yaml config/schedule.yaml
```

### Если example-файла нет: полное содержимое

Ниже — весь `config/schedule.example.yaml`; при потере файла его можно
восстановить копированием этого листинга:

```yaml
# Расписание автоматического управления Time-менеджером.
# Можно создать несколько YAML-файлов в каталоге config/ — они объединяются,
# поздние файлы переопределяют скалярные значения и дополняют tasks.
#
# Рабочий день НЕ создается здесь: он появляется сам — по отметке СКУД
# или в момент начала удалённого дня (роботы портала).

timezone: Europe/Moscow

schedule:
  # Локальное время ежедневного прогона демона.
  apply_time: "18:05"
  # Сколько дней вперёд выставлять (включая сегодня).
  horizon_days: 2
  # Сколько прошедших дней догонять после простоя (создаст только отсутствующее).
  backfill_days: 1
  # Через сколько минут повторить прогон после ошибки.
  retry_minutes: 20

tasks:
  # Удалённая работа по пятницам: выставляется заранее, день привяжут роботы.
  - kind: remote
    days: [fri]
    start: "09:00"
    end: "18:00"
    comment: "Удалённая работа"

  # Учет времени: записывается, как только за дату появился рабочий день
  # (СКУД или удалёнка); до этого прогон просто пропускает день и повторит позже.
  # Записи за день суммируются! Если за дату уже есть любая запись учета
  # (вручную, старым ботом), новая НЕ добавляется (on_existing_entries: skip).
  - kind: time_entry
    days: [mon-fri]
    contract:
      entity_type: 1298
      id: 123
    description: "Общие задачи"
    hours: 7
    minutes: 30
    on_existing_entries: skip
```

### Справочник полей

#### Верхний уровень

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `timezone` | строка | `Europe/Moscow` | Часовой пояс, в котором трактуются даты и время расписания. Должна совпадать с `BITRIX_TIMEZONE` в `.env`. |
| `schedule` | секция | см. ниже | Когда и за какой промежуток дат выполняет прогоны демон. |
| `tasks` | список | `[]` | Операции: удалёнка и учет времени. Порядок применения внутри дня фиксирован: `workday`, `remote`, `time_entry`. |

#### Секция `schedule`

| Поле | Диапазон | По умолчанию | Описание |
|---|---|---|---|
| `apply_time` | `HH:MM` | `18:05` | Локальное время ежедневного прогона демона. |
| `horizon_days` | 0–30 | `2` | Сколько дней **после** сегодняшнего входит в окно прогона (граница `сегодня + horizon_days`, включительно). |
| `backfill_days` | 0–30 | `1` | Сколько прошедших дней перед сегодняшним догоняется после простоя (создаётся только отсутствующее — записи идемпотентны). |
| `retry_minutes` | 1–720 | `20` | Пауза перед повтором прогона после сбоя. |

Окно одного прогона: даты с `сегодня − backfill_days` по `сегодня +
horizon_days` включительно, от старых к новым. При значениях по умолчанию
(1 и 2) это вчера, сегодня, завтра и послезавтра.

#### Список `tasks`

Общие поля любой задачи:

| Поле | Обязателен | Описание |
|---|---|---|
| `kind` | да | `remote` или `time_entry` (значение `workday` существует, но не используется — см. ниже). |
| `days` | да | Дни недели: строка или список. Имена `mon…sun` или `пн…вс`, диапазоны через дефис: `[mon-fri]`, `[sat, sun]`. Диапазон через границу недели тоже работает: `fri-mon` = пт, сб, вс, пн. |

Поля задачи `kind: remote` (удалённая работа, создаётся заранее; рабочий день
к ней привяжут роботы портала):

| Поле | Обязателен | По умолчанию | Описание |
|---|---|---|---|
| `start` | да | — | Начало `HH:MM`, локальное время. |
| `end` | да | — | Окончание `HH:MM`; должно быть позже `start` в пределах той же даты. |
| `comment` | нет | `""` | Комментарий к интервалу удалёнки. |

Поля задачи `kind: time_entry` (запись учета времени; добавляется к уже
существующему рабочему дню — если дня ещё нет, дата пропускается и
догоняется позже):

| Поле | Обязателен | По умолчанию | Описание |
|---|---|---|---|
| `contract.entity_type` | да | — | Тип сущности договора: `1048` и `1052` — карточки договоров, `1298` — шаблоны. |
| `contract.id` | да | — | Числовой ID карточки/шаблона в смарт-процессе (не текстовый номер договора). |
| `description` | да | — | Текст записи учета. |
| `hours` | да | `0` | Целые часы, 0–24. |
| `minutes` | нет | `0` | Только `0` или `30`. Сумма `hours + minutes` должна быть больше нуля. |
| `on_existing_entries` | нет | `skip` | `skip` — если за дату уже есть хоть одна запись учета (вручную или старым ботом), новая не добавляется; `append` — добавлять поверх существующих (портал суммирует записи за день!). |

Ограничения валидации, о которых стоит знать заранее:

- неизвестные поля запрещены — опечатка (`hour:` вместо `hours:`) завершит
  запуск ошибкой конфигурации, а не молчанием;
- `remote` без `start`/`end` или с `end <= start` не пройдёт проверку;
- `time_entry` без `contract` или с пустым `description` — тоже;
- пустой список `days` или неизвестное имя дня — ошибка.

#### `kind: workday` — не использовать

Значение существует в коде (ручной обычный рабочий день), но на этом портале
не работает: `crm.item.add` в смарт-процесс рабочих дней возвращает
`ACCESS_DENIED` (у вебхука нет туда прав записи), а в типовом сценарии день
и не нужен — он создаётся сам по отметке СКУД или роботами удалёнки.

### Как найти `contract.entity_type` и `contract.id`

Идентификатор договора — это ID карточки плюс тип смарт-процесса, а не
текстовый номер договора. Быстрее всего — поиск командой SDK (только
чтение). В Docker SDK доступен как модуль:

```bash
docker compose run --rm --entrypoint python bitrix-auto \
  -m bitrix_time_manager contracts 'Общие задачи' --type 1298
```

Локально после `pip install -e '../sdk-bitrix-time-manager'` доступна
та же команда в виде утилиты `bitrix-time`:

```bash
bitrix-time contracts 'Общие задачи' --type 1298
```

Команда печатает найденные карточки с их ID и названием — их и подставляйте
в задачу `time_entry`. Альтернатива — открыть
карточку на портале и взять числовой ID из её адреса.

### Проверка расписания до запуска

В контейнере каталог настроек — `/app/config` (смонтирован `./config`),
поэтому `--config` указывать не нужно:

```bash
docker compose run --rm bitrix-auto preview                  # окно из schedule
docker compose run --rm bitrix-auto preview --date 2026-10-23 --days 1
docker compose run --rm bitrix-auto apply   --date 2026-10-23 --days 1
```

Локально те же команды с явным путем: `bitrix-auto preview --config
config/schedule.yaml --date 2026-10-23 --days 1`.

`preview` показывает план без записей (`status: preview`), `apply` создаёт
записи идемпотентно — повторный запуск вернёт `existing`, дублей не будет.
