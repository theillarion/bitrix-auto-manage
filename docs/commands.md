# Команды bitrix-auto: справочник CLI

Полный справочник команд `bitrix-auto`. Источник истины — код интерфейса
`src/bitrix_auto_manage/cli.py`; при расхождении справочника с поведением
команд верен код.

Вызвать CLI можно тремя способами:

- утилитой `bitrix-auto` из активированного venv: склонируйте SDK рядом
  с репо (см. [README](../README.md)) и поставьте оба пакета командой
  `pip install -e '../sdk-bitrix-time-manager' -e .`;
- эквивалентно — `python -m bitrix_auto_manage`;
- в Docker: точка входа контейнера уже `python -m bitrix_auto_manage`,
  поэтому любая команда даётся как `docker compose run --rm bitrix-auto
  <команда> [<флаги>]`; каталог настроек в контейнере — `/app/config`,
  флаг `--config` не нужен.

Настройки команда берёт из двух мест: переменные окружения с вебхуком
(файл `.env`; раздел «Переменные окружения» ниже) и YAML-расписание
(каталог `config/`; полный справочник полей — [docs/setup.md](setup.md)).
Здесь описан только CLI `bitrix-auto`; утилита `bitrix-time` из соседнего
SDK — отдельная программа (см. README SDK).

## Сводная таблица команд

| Команда | Назначение | Записи на портал |
| --- | --- | --- |
| `check` | Проверить соединение, вебхук и схему портала | нет — только чтение |
| `preview` | Показать план записей для окна дат | нет — сухой прогон |
| `apply` | Создать записи окна дат (идемпотентно) | да |
| `show` | Показать рабочий день, удалёнку и учет времени за дату | нет — только чтение |
| `daemon` | Прогон окна каждый день в `schedule.apply_time` | да |

Все команды, кроме `daemon`, читают YAML-настройки при старте — ошибка
YAML завершает команду с кодом 1 до обращения к порталу. Демон настройки
читает сам, перед каждым прогоном (раздел «daemon»).

## Общие флаги

Общие флаги доступны у каждой подкоманды и указываются **после** неё:
`bitrix-auto check --config config/schedule.yaml` — верно, а
`bitrix-auto --config config check` — уже ошибка аргументов (exit 2):
до подкоманды допустимы только `-h/--help` и `--version`. Запуск совсем
без подкоманды — тоже ошибка аргументов (exit 2).

| Флаг | Дефолт | Описание |
| --- | --- | --- |
| `--config PATH` | `./config` | YAML-файл или каталог настроек; можно повторять |
| `--env-file PATH` | `.env` | Файл окружения; несуществующий путь молча игнорируется |
| `-v`, `--verbose` | выключен | Подробный журнал отладки (DEBUG вместо INFO); журнал выводится в stdout |
| `-h`, `--help` | — | Справка по команде |

`--version` — глобальный флаг до подкоманды: печатает `bitrix-auto 0.4.1`
и завершает работу с кодом 0.

Правила `--config`:

- флаг можно повторять: файлы и каталоги обрабатываются в порядке указания;
- каталог разворачивается в свои `*.yaml`/`*.yml` **по алфавиту**; файлы
  с `.example.` в имени игнорируются — это шаблоны, а не настройки;
- пустой каталог или несуществующий путь — ошибка конфигурации (exit 1);
- при слиянии нескольких файлов скалярные значения и секция `schedule`
  позднего файла перезаписывают ранние, а списки `tasks` объединяются;
  `skip_dates` — поле секции `schedule`, поэтому заменяется целиком.

Подробнее о загрузке настроек — [docs/setup.md](setup.md), раздел
«Где живёт и как загружается».

## check

Проверить соединение, вебхук и схему портала без записей.

```
bitrix-auto check [--config PATH] [--env-file PATH] [-v]
```

Аргументы — только общие флаги. Команда читает YAML-настройки, затем
обращается к порталу только на чтение: проверяет владельца вебхука
(`profile`), схему смарт-процессов (поля рабочих дней, удалёнки и учета
времени) и доступность метода `crm.item.add`.

Вывод — JSON в stdout с ключами `portal`, `user_id`, `timezone`,
`schema_ok`, `create_method`, `writes_enabled`, `note`; успешная проверка
отмечается `schema_ok: true`.

```bash
# локально
bitrix-auto check

# в Docker
docker compose run --rm bitrix-auto check
```

## preview

Показать, что будет создано для окна дат, без записей (сухой прогон).

```
bitrix-auto preview [--config PATH] [--env-file PATH] [-v] [--date YYYY-MM-DD] [--days N]
```

| Аргумент | Дефолт | Описание |
| --- | --- | --- |
| `--date YYYY-MM-DD` | из расписания | Начало окна дат |
| `--days N` | `1` при явном `--date`, иначе из расписания | Сколько дней от начала окна |

Семантика окна — в разделе «Окно дат»: без флагов берётся окно из
`schedule`, `--date`/`--days` задают его явно. Даты из
`schedule.skip_dates` исключаются из прогона и здесь — включая явно
заданные окна `--date`/`--days`; в журнале такая дата отмечается строкой
`<дата>: skipped by skip_dates`.

В журнал пишется `Preview run, no writes.`; операции уходят в SDK в режиме
без записи (`status: preview`). Итог — строка счётчиков вида:

```
created=0 existing=0 previewed=4 skipped=0 uncertain=0 failed=0
```

| Счётчик | Смысл |
| --- | --- |
| `created` | создано записей (в `apply`) |
| `existing` | запись уже существовала — повторный прогон не создал дубль |
| `previewed` | операция выполнена в режиме без записи |
| `skipped` | операция пропущена: нет рабочего дня (догонится позже), сработала защита `on_existing_entries: skip` или операция завершилась ошибкой |
| `uncertain` | потерянный ответ портала: операция остановлена, автоповтор заблокирован SDK |
| `failed` | неудачный прогон целиком; в строке `preview`/`apply` всегда 0 — ошибки отдельных операций идут в `skipped`/`uncertain`, а `failed=1` ставит демон при ошибке загрузки конфигурации |

При `uncertain` разблокировка — вручную командой `bitrix-time resolve`
из SDK (см. README SDK).

```bash
# план на окно из расписания (сегодня-1 .. сегодня+2 при дефолтах)
bitrix-auto preview --config config/schedule.yaml

# план на конкретную дату
bitrix-auto preview --config config/schedule.yaml --date 2026-10-23 --days 1

# в Docker (--config не нужен: контейнер видит /app/config)
docker compose run --rm bitrix-auto preview --date 2026-10-23 --days 1
```

## apply

Реально создать записи для окна дат (идемпотентно).

```
bitrix-auto apply [--config PATH] [--env-file PATH] [-v] [--date YYYY-MM-DD] [--days N]
```

Аргументы — те же, что у `preview` (таблица выше и раздел «Окно дат»).
Отличие — записи создаются:

- разрешение записи CLI включает сам на время прогона — задавать
  `BITRIX_ALLOW_WRITES` вручную не нужно; `preview`, `check` и `show`
  всегда только читают;
- идемпотентность: у каждой операции стабильный ключ `auto:<дата>:<хэш>`;
  повторный прогон возвращает `existing`, дублей не создаёт;
- `time_entry` добавляется только к уже существующему рабочему дню: если
  дня ещё нет (он появляется по отметке СКУД или от роботов удалёнки),
  дата пропускается и догоняется позже (`backfill_days`);
- защита `on_existing_entries: skip` (по умолчанию): если за дату уже есть
  любая запись учета — новая не добавляется (счётчик `skipped`);
  `append` — добавляет поверх существующих (портал суммирует записи за
  день);
- `schedule.skip_dates` исключает даты из прогона — включая явные окна
  `--date`/`--days`.

Итог — та же строка счётчиков, что у `preview`.

```bash
# применить окно из расписания
bitrix-auto apply --config config/schedule.yaml

# одна конкретная дата
bitrix-auto apply --config config/schedule.yaml --date 2026-10-23 --days 1

# в Docker
docker compose run --rm bitrix-auto apply --date 2026-10-23 --days 1
```

## show

Показать рабочий день, удалёнку и учет времени за дату (только чтение).

```
bitrix-auto show [--config PATH] [--env-file PATH] [-v] [--date YYYY-MM-DD]
```

| Аргумент | Дефолт | Описание |
| --- | --- | --- |
| `--date YYYY-MM-DD` | сегодня по часам хоста | Дата дня |

Внимание: без `--date` берётся дата хоста (`date.today()`), а не дата
в часовом поясе YAML — не так, как считается окно `preview`/`apply`/`daemon`.
На хосте в другом поясе поздним вечером или ранним утром даты могут
разойтись; указывайте `--date` явно.

Вывод — JSON в stdout с ключами `day`, `workday`, `remote`,
`time_entries`: `workday` — рабочий день или `null`, `remote` — интервалы
удалёнки, `time_entries` — записи учета; при ошибке чтения записей вместо
списка в `time_entries` будет строка с текстом ошибки.

```bash
# локально
bitrix-auto show --date 2026-10-23

# в Docker
docker compose run --rm bitrix-auto show --date 2026-10-23
```

## daemon

Постоянный режим: прогон окна каждый день в `schedule.apply_time`.

```
bitrix-auto daemon [--config PATH] [--env-file PATH] [-v] [--once]
```

| Аргумент | Дефолт | Описание |
| --- | --- | --- |
| `--once` | выключен | Один прогон окна и выход (для cron/планировщика ОС) |

У демона нет `--date`/`--days`: прогон всегда покрывает окно из расписания
(`сегодня−backfill_days .. сегодня+horizon_days`; «сегодня» — по часовому
поясу YAML, см. раздел «Окно дат»).

Цикл демона:

1. Прогон выполняется сразу при старте.
2. Перед каждым прогоном — включая первый — YAML-конфиг перечитывается:
   правки расписания подхватываются без рестарта. Ошибка загрузки
   считается неудачным прогоном: причина пишется в журнал, ранее
   загруженный конфиг повторно не применяется, следует пауза
   `retry_minutes` и повтор. Битый конфиг на первом старте (когда
   валидного ещё не было) завершает демон с кодом 1.
3. Успешный прогон — пауза до следующего `schedule.apply_time` (локальное
   время часового пояса YAML); если до `apply_time` осталось 30 секунд
   или меньше (либо оно уже наступило), следующий прогон назначается
   на завтра.
4. Неудачный прогон — повтор через `schedule.retry_minutes` (по умолчанию
   20 минут).
5. Несовпадение `timezone` в YAML и `BITRIX_TIMEZONE` отмечается
   предупреждением в журнал.

`daemon --once` выполняет ровно один прогон и выходит: код 0 при успешном
прогоне, 1 — при неуспешном (`failed` или `uncertain` больше нуля). Это
режим для cron/Планировщика Windows (пример cron: `5 18 * * *`).

```bash
# постоянный режим локально
bitrix-auto daemon --config config/schedule.yaml

# один прогон (для cron)
bitrix-auto daemon --config config/schedule.yaml --once

# демон в Docker (постоянный сервис)
docker compose up -d --build

# разовый прогон в контейнере
docker compose run --rm bitrix-auto daemon --once
```

## Окно дат: --date, --days и расписание

Окно прогона `preview`/`apply` — список дат, для которых выполняются
задачи расписания (по дням недели `tasks[].days`). Три способа задать окно:

| Комбинация | Окно |
| --- | --- |
| `--date D` без `--days` | один день: `D` |
| `--date D --days N` | `D, D+1, …, D+N−1`; при `N < 1` — сообщение `--days must be at least 1.` и exit 1 |
| `--days N` без `--date` | `сегодня, …, сегодня+N−1` («сегодня» — по часовому поясу YAML); `N < 1` не проверяется — окно пустое, прогон завершится нулевой строкой счётчиков |
| без обоих флагов | окно из расписания: `сегодня−backfill_days .. сегодня+horizon_days` включительно |

Даты из `schedule.skip_dates` исключаются из прогона во всех командах —
`daemon`, `apply` и `preview`, включая явные окна `--date`/`--days`.

Поля секции `schedule`, влияющие на окно и цикл демона (полный справочник
всех полей YAML — [docs/setup.md](setup.md)):

| Поле | Дефолт | Диапазон | Смысл |
| --- | --- | --- | --- |
| `apply_time` | `18:05` | — | локальное время ежедневного прогона демона |
| `horizon_days` | `2` | 0–30 | сколько дней после сегодняшнего входит в окно |
| `backfill_days` | `1` | 0–30 | сколько прошедших дней перед сегодняшним входит в окно |
| `retry_minutes` | `20` | 1–720 | пауза повтора после неудачного прогона |
| `skip_dates` | `[]` | список дат | даты, полностью исключаемые из планирования |

## Коды выхода

| Код | Когда |
| --- | --- |
| `0` | успех (включая `--version` и `-h`) |
| `1` | ошибка приложения: битый или отсутствующий YAML, отсутствие `BITRIX_WEBHOOK_URL`, ошибка портала; также `--date D --days N` при `N < 1` (`--days must be at least 1.`) |
| `2` | ошибка аргументов: неизвестная команда или флаг, общий флаг до подкоманды, отсутствие подкоманды, неверный формат `--date` |
| `130` | процесс остановлен Ctrl+C |
| `daemon --once` | `0` — успешный прогон; `1` — неуспешный (`failed`/`uncertain` больше нуля) |
| `daemon` | `1` — битый конфиг на первом старте; иначе работает до остановки |

Примеры ошибок аргументов (код 2):

```
bitrix-auto: error: argument command: invalid choice: 'bogus' (choose from 'check', 'preview', 'apply', 'show', 'daemon')
bitrix-auto preview: error: argument --date: Invalid date '21.10.2026'; expected YYYY-MM-DD.
```

## Переменные окружения

Читаются SDK из процесса и из файла `--env-file` (дефолт `.env`; шаблон —
`.env.example` в корне репо). Полная таблица переменных с дефолтами —
[README](../README.md#5-настройки-окружения-env), раздел «Настройки
окружения (`.env`)»; как создать вебхук — [docs/setup.md](setup.md),
Часть 1. Здесь — только два правила, которых нет в README:

- значения из `--env-file` **не переопределяют** уже экспортированные
  переменные окружения процесса: если переменная задана в среде, значение
  из файла игнорируется;
- `BITRIX_ALLOW_WRITES` вручную не нужна: CLI включает запись сам на время
  прогона `apply`/`daemon` (`preview`, `check` и `show` всегда только
  читают); допустимы `true`/`false`/`1`/`0`.
