## 2. Сводка состояния безопасности

Пара «обёртка + SDK» — одиночный самохостимый инструмент с одним кредом (входящий вебхук Bitrix24, bearer-в-URL). Архитектурные инварианты в целом крепкие: единственный write-метод (`crm.item.add`) за двойным гейтом, идемпотентность на трёх уровнях (operation_id/xmlId/request_keys), SQL полностью параметризован, `yaml.safe_load`, `extra="forbid"`, редакция секрета в логах/ошибках, owner-scoping всех записей. Ни одного секрета за всю историю git не закоммичено; живых секретов в рабочих деревьях нет.

Реальные дефекты сосредоточены в трёх кластерах: (1) обработка «чужих» исключений и граничных значений портала — не-`TimeManagerError` роняет демон целиком (ValueError из DST-пробелов, коэрций `int()`, pydantic-валидации), `isdigit`/`int` расходятся на Unicode-цифрах; (2) слепая зона контроля перекрытий удалёнки для «висящего» интервала с прошлых суток — пишутся лишние записи в прод-портал; (3) гигиена локальных артефактов — журнал (персональные данные о рабочем времени) создаётся 0644, а в обёртке путь по умолчанию `.state/` вообще не в `.gitignore` (один `git add -A` до публикации данных); плюс реальные идентификаторы портала остаются достижимы в опубликованной истории git.

## 5. Опровергнутые кандидаты (2)

- `bitrix_time_manager.client:webhook-log-filter-child-logger-bypass` — предпосылка верна (фильтры родителя не действуют на дочерние логгеры), но сток не существует: в установленном httpcore 1.0.9 `Request.__repr__` содержит только метод; URL-несущая запись идёт через фильтруемый логгер `httpx`. Харнесс охотника использовал формат сообщения, который httpcore не создаёт. Остаточная ценность — hardening (см. §6).
- `config.from_env.env-file-unscoped-env-keys` (прошлый аудит, needs_validation) — механика реальна (незакопленный `load_dotenv` действительно управляет SSL_CERT_FILE/прокси через httpx trust_env), но во всех документированных деплоях писатель `.env` — тот же принципал, что задаёт сам вебхук: пересечения границы нет.

## 6. Hardening-заметки (не находки) и позитивные паттерны

Позитивные: параметризованный SQL; `yaml.safe_load` + `extra="forbid"`; двойной write-гейт; трёхуровневая идемпотентность и анти-«воскрешение»; редукция вебхука (SecretStr/redact/log-filter/`from None`); owner-scoping; offline-тесты с запретом сети; CI без секретов; ни одного секрета в истории.

Hardening (по приоритету):
1. **Вне репо, срочно**: `../backup-pre-rewrite-2026-10-20/` — `sdk-env-backup.txt` (358 байт, совпадает размером с `.env` SDK — вероятная plaintext-копия вебхука), git-бандлы с до-нейтрализационной историей, карты замен. Защитить/уничтожить; при подтверждении копии — ротация вебхука.
2. `chmod 0600/0700` журнала при создании (дублирует фикс находки 8); политика ретеншна для журнала и stdout-логов (LIM-08/TODO).
3. Docker: `user:` в compose/USER в Dockerfile; `logging:` с max-size/max-file; смонтировать только `src/` SDK; `.dockerignore`.
4. Compose-интерполяция читает тот же `.env`, что содержит секрет (BITRIX_SDK_PATH) — фильтровать ключи `load_dotenv` до `BITRIX_*` или `trust_env=False` в AsyncClient; задокументировать.
5. Расширить установку log-фильтра на дочерние логгеры `httpcore.*` (defence-in-depth после опровержения кандидата).
6. Обёртка: зеркалить лимиты SDK (4000 симв.) в `TaskSection`; валидировать timezone на загрузке; учитывать `skipped` в `RunSummary.ok`; симметричная валидация `--days`; exit≠0 при ошибках apply (cron не видит failures).
7. SDK: резервировать префикс `auto:` для ручных `--idempotency-key`; проверять owner по-элементно в `list_remote_work`/overlap-скан; кап страниц/элементов в `list_items`.
8. Паблик-репо: `.mimosa/` в оба `.gitignore` (сейчас покрывется только машинно-глобальным ignore!); `state/` в .gitignore SDK; `.lock-task`; фиксация CI-actions по SHA; lockfile/digest-pinning; объявить SDK зависимостью обёртки или fail-fast.
9. Документация: реальный host-путь журнала `.state/` (README:141/149 вводят в заблуждение); cron-пример без `cd`; PortalSchema как принятая публикация идентификаторов — задокументировать осознанно.
